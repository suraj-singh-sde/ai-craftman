# Running AI-Craftman in Codex

This plugin was written for Claude Code and generated for Codex. The pipeline, the state machine (`craftman-state`), the memory layout, the gates and the guards are the same. What differs is below; read it before section 0 of the pipeline text.

- **Plugin root.** The SessionStart hook writes the installed plugin's path to `~/.codex/ai-craftman.root`, and to `.craftman/.plugin-root` once the project has `.craftman/`. `PR` in the pipeline text means that path. Run the state machine as `"$PR/bin/craftman-state"` (the bare name is not on PATH), and read templates from `$PR/templates/`.
- **Agents.** Every `craftman-<name>` agent is a custom agent in `.codex/agents/craftman-<name>.toml`, installed into the project by `$craftman-init`. Where the pipeline text says "dispatch", "a fresh agent" or "spawn", spawn that custom agent with the inputs the text lists: "Spawn the craftman-architect agent with: level hld, requirements <path>, context <path>, standards <paths>, out <path>". Spawn the agents of one group in the same turn so they run in parallel. A follow-up to a running agent (the text's "follow-up message to the agent's thread") is `send_input`; it counts against the budget like a spawn. Never do an agent's work yourself.
- **Models.** The agent files carry `model_reasoning_effort` and a commented `model` line with the tier: strong (Claude Code: opus) for architect, requirements-planner, security-reviewer; mid (sonnet) for builders, reviewers, QA and the rest; fast (haiku) for triage, human-liaison, human-oversight, memory-keeper. Set `model` in those files, or `[agents] default_subagent_model` in `~/.codex/config.toml` for the mid tier. Where the text says "your strong-tier model", spawn with that model; "your mid-tier model", the default.
- **Settings.** `model_tier` and `max_agent_calls` come from `.craftman/governance.md` (defaults `balanced` and `60`); there is no plugin setting.
- **Questions to the human.** Use `request_user_input` with the liaison's questions, exactly as written, when the session has that tool. When it does not (some Codex versions allow it only in Plan mode): run `"$PR/bin/craftman-state" ask "<question text>" "<option 1>|<option 2>|..."` for ONE question, print the question and its options, and end your turn. The human answers in their next message; the UserPromptSubmit hook matches it to an option and records it in `answers.md` (an `[APPROVAL:<category>]` question answered "Approve" becomes a grant in `approvals.md`). On the next turn read `answers.md` and continue the pipeline where you stopped. Several questions: one `ask` per turn, in the liaison's order.
- **Enforcement that differs.** Codex tool hooks do not name the agent that is running a tool. So: while any builder, reviewer or package lead is active (the SubagentStart/Stop hooks track them in `.craftman/.agents-active`), the hidden suite is refused to every tool call, including yours: run `craftman-state verify hidden` between groups, not while a group runs. The test-file lock for code-writer, the evidence-ownership rule and the e2e-verifier write rule are prompt-only here. `apply_patch` is checked for the control files and secrets like Claude's write tools. The deploy guard, the agent budget, the engineering hold and the gates in `craftman-state` are identical.
- **Tools that do not exist here.** The task list (`TodoWrite`): keep the step list in your plan. `WebSearch`/`WebFetch` in research-agent: Codex's own web search, and the context7 tools when configured. Git worktrees, `gh`, Docker: the same commands.
- **Unverified on a real Codex run** (first run to confirm): the exact spawn payload field names the budget hook matches (`agent_type`, `agent`, `role`, `name`, `profile` are all accepted), the `request_user_input` answer shape (several shapes are accepted; `ask` is the fallback), and whether `${PLUGIN_ROOT}` is set for hook commands of a marketplace-installed plugin (the official docs say it is).
